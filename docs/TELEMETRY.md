# Подключение фактических показаний турбин

Сайт умеет принимать измерения WT-01 и WT-02 через обновляемый файл или защищённый входящий API. Источник должен предоставлять **фактическую мощность и исходное время измерения**. Прогноз погоды, ответ языковой модели и прогноз CatBoost не являются измерениями мощности.

В поставленных данных `task` последние измерения относятся к 31 января 2026 года. Пока нет свежих показаний станции, статус «Текущие показания турбин не подключены» корректен. Настройка соединения сама по себе не делает данные доступными.

## Что запросить у владельца станции

- Выгрузку измерений или возможность отправлять их с сервера станции.
- Соответствие оборудования идентификаторам `WT-01` и `WT-02`.
- Время каждого измерения с часовым поясом, например `2026-09-23T17:00:00+05:00`.
- Фактическую мощность и номинальную мощность турбины, если значения передаются в кВт.

Входной формат WindOps использует `power = измеренная мощность / номинальная мощность`, от 0 до 1. Значение `0` — полноценное измерение. `72` нельзя передавать вместо `0.72`. Дополнительные поля: `windSpeed` в м/с, `windDirection` в градусах, `temperature` в °C.

## Вариант 1: обновляемый CSV или JSON

В `backend/.env` задайте путь к файлу и перезапустите `npm run dev`:

```dotenv
WINDOPS_TELEMETRY_FILE=storage/telemetry/incoming.csv
WINDOPS_TELEMETRY_MAX_AGE_SECONDS=1200
```

Относительный путь считается от корня проекта; можно использовать абсолютный путь. Файл не создаётся автоматически: его должен обновлять источник измерений. Секрет API в этом режиме не нужен.

CSV содержит заголовок и последние показания. Пример формата **на архивных измерениях** (они будут отмечены как устаревшие):

```csv
turbineId,timestamp,power
WT-01,2026-01-31T18:00:00Z,0.2
WT-02,2026-01-31T18:00:00Z,0.2
```

Для JSON используется тот же контракт, что и у API:

```json
{
  "readings": [
    {"turbineId": "WT-01", "timestamp": "2026-01-31T18:00:00Z", "power": 0.2},
    {"turbineId": "WT-02", "timestamp": "2026-01-31T18:00:00Z", "power": 0.2}
  ]
}
```

Укажите путь к `.json` вместо `.csv`, если источник формирует JSON. Сохраняйте небольшой снимок последних измерений: максимум 2000 записей и 2 МиБ. Для обновления сначала запишите временный файл, затем атомарно замените основной — так сервер не прочитает частично записанные данные. Само обновление файла не требует перезапуска.

**Не заменяйте архивные даты сегодняшними.** Для текущего режима нужны новые измерения с их настоящими отметками времени.

## Вариант 2: отправка измерений по API

Оставьте `WINDOPS_TELEMETRY_FILE` пустым. В `backend/.env` задайте отдельный случайный `WINDOPS_TELEMETRY_KEY`. Можно сгенерировать секрет локально:

```powershell
node scripts/python.mjs -c "import secrets; print(secrets.token_urlsafe(32))"
```

Поместите результат в `.env` и настройте тот же секрет на отправляющем сервере. Перезапустите backend после изменения настроек. Этот ключ не связан с NVIDIA или OpenAI и не требует регистрации у внешнего провайдера.

Сервер станции отправляет `POST /api/telemetry` с JSON выше и заголовком `X-Telemetry-Key`. Передавайте реальные новые измерения, сохраняя время источника. Если готовый JSON находится в `incoming.json`, отправка из PowerShell выглядит так:

```powershell
Invoke-RestMethod -Method Post `
  -Uri 'http://127.0.0.1:8000/api/telemetry' `
  -Headers @{ 'X-Telemetry-Key' = $env:WINDOPS_TELEMETRY_KEY } `
  -ContentType 'application/json' `
  -InFile 'incoming.json'
```

Отправляющий процесс должен иметь переменную окружения `WINDOPS_TELEMETRY_KEY`; PowerShell не загружает её из backend/.env автоматически. Ключ хранится на серверах, не передаётся frontend и не коммитится в Git. При сетевом размещении используйте HTTPS и доступ только для доверенного отправителя; локальный `npm run dev` слушает loopback.

Ответ сообщает `accepted`, `ignored` и состояние канала. Более старые и повторные записи не заменяют последнее измерение. API сохраняет последние значения в `storage/telemetry/latest.json`, поэтому они переживают перезапуск. В режиме файла POST возвращает `409`, чтобы не перезаписывать внешний источник. Без настроенного ключа — `503`, с неверным ключом — `401`, при ошибочных измерениях — `422`.

## Проверка подключения

Откройте «Диагностика → Текущие показания турбин» или выполните:

```powershell
Invoke-RestMethod 'http://127.0.0.1:8000/api/telemetry' | ConvertTo-Json -Depth 6
```

| Статус API | Значение |
| --- | --- |
| `not_configured` | Не настроен источник и нет полученных показаний. |
| `waiting` | Настройки есть, измерения ещё не поступили. |
| `partial` | Свежие показания есть только у одной турбины. |
| `connected` | Свежие показания получены для обеих турбин. |
| `stale` | Полученные измерения старше допустимого срока. |
| `error` | Файл недоступен или показания не прошли проверку. |

По умолчанию срок свежести — 20 минут. Он настраивается через `WINDOPS_TELEMETRY_MAX_AGE_SECONDS` (минимум 60 секунд). Считается **возраст измерения**, а не время загрузки файла или запроса. Время без часового пояса и показания из будущего отклоняются. Новая запись не заставляет модель пересчитывать прогноз и не вызывает языковую модель.

Панель получает состояние при обычном опросе API (примерно каждые 5 секунд), фоновая проверка источника и события агента работают каждые 15 секунд. Для просроченных/недоступных значений `observed` и `observedAt` равны `null`; последняя принятая запись сохраняется отдельно в `measurement` с датой и состоянием. `lastObservation` по-прежнему содержит архив исследования.

Подключение измерений не подтверждает исправность оборудования. Текущие показания и прогноз на следующий час нельзя автоматически сравнивать как значения одного момента. До реализации проверки совпадающих времён и интервалов усреднения состояние оборудования остаётся `unknown`, а `twinConsistency` — недоступным. Приём данных сам по себе не повышает индикатор надёжности прогноза.
